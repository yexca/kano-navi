Kano Navi v0.2.0 replaces the TypeScript backend with a Go service that serves
the whole site from one process, redesigns the public pages, rebuilds the
operator console around tasks, and adds YouTube push notifications.

<details>
<summary><strong>Public pages</strong></summary>

- `/`, `/history` and `/about` share one site shell with page navigation, a
  live Japan-time clock and the preference controls.
- The board opens on a ticket for what airs next, with the Japan time, the
  visitor's local time and a countdown, beside a profile card.
- The schedule is a Monday-first program guide with a Week/Month switch; every
  entry shows its type, status, cancellation notes and provenance.
  `/api/calendar` now accepts an inclusive range of up to 42 Japan dates.
- `/history` gets an identity picker, a year rail and a masonry gallery whose
  dialog keeps every provenance field.

</details>

<details>
<summary><strong>Operator console</strong></summary>

- The console is organized into Overview, Review queue, Schedule, Content,
  Runs & workflows, Sources and Models & detection, with light and dark themes
  and English and Chinese copy.
- The overview lists what needs attention: pending schedule images, suspected
  cancellations, failed posts, source health, the active run and the next
  timer.
- Runs are a single resource: syncs, scans, saved workflows and source fetch
  windows start through the single-flight queue and can be cancelled and
  retried. Jobs survive a restart and report per-step progress.
- The mobile navigation scrolls inside its own strip.

</details>

<details>
<summary><strong>Synchronization and extraction</strong></summary>

- A failed X or YouTube step is recorded and the remaining steps still run;
  the job finishes as partial instead of failed.
- Historical `before` and `range` windows use the official X and YouTube APIs
  when their credentials are configured, with resumable page checkpoints.
- YouTube WebSub push, enabled in Content & media, queues a YouTube sync as
  soon as a new upload or reservation is announced. Polling remains the
  baseline.
- The public YouTube feed is retried on transient upstream failures.
- An opt-in all-posts mode sends every X post with text or images to the
  message model, and the model receives each post's Japan date, weekday and
  time.
- Anthropic extraction requests work with newer Claude models that reject a
  forced tool choice.
- Pending media downloads start with the newest videos and posts, and legacy
  schedule records without an image are no longer reported as a permanent
  image error.

</details>

<details>
<summary><strong>Runtime and development</strong></summary>

- The production image is a scratch image with the `kano-go` binary, the built
  frontend and the bundled assets, and its health check runs
  `kano-go healthcheck`.
- `make start`, `make seed` and `make sync` run the Go binary; development runs
  Vite in front of the Go backend. `make ci-backend` runs the Go tests and vet.
- MCP `serverInfo` reports the package.json version, which every Go build now
  injects at link time.
- Releases verify that the tag matches package.json and that the commit is on
  `main`, and publish this tracked note as the GitHub Release body.

</details>

## Upgrading from a TypeScript release

Releases up to 0.1.3 shipped a Node image. The Go image accepts the same
environment and `/app/data` volume, so `docker-compose.yml` and `.env` are
unchanged. Back up `./data`, then update as usual; the first start upgrades
the snapshot in place and keeps every record, provider and workflow. Provider
keys stay readable with the same `LLM_SECRETS_KEY`.

## Rolling back to 0.1.3

To roll back, stop the container and pin the previous image with
`KANO_IMAGE=yexca/kano-navi:0.1.3`.

The last TypeScript release image (`yexca/kano-navi:0.1.3`) runs on the same
`data/` directory; its source is the `v0.1.3` tag. Stop the Go process first:
only one process may own a snapshot, since both write SQLite and both would
start timers. That release reads the `workflows` table, which Go releases
leave as they found it, so its saved workflows and their timers run again; it
ignores the per-source `source_schedules` of later releases.

The additive `workflow_*` tables and columns are ignored by that release, and
provider secrets use the same encryption format in both directions. A legacy
`events` table that was rebuilt on upgrade is already in the layout 0.1.3
expects.
